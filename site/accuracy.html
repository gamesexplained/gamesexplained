How listings are checked

Trusting a listing

A game's page makes two claims about its Source tab: how much of the program it explains, and how much of that explanation is right. This page shows how each is measured, and how the About tab keeps a ledger of every step behind the listing, with examples from C64 games on the site.

The listing

A game’s Source tab is its listing: every byte of the program, in memory order, each with what it is. Code is shown as instructions, and tables and variables as bytes. A comment on the first address of a routine or table describes the whole of it, and the bytes up to the next label belong to it.

$2495A2 00update_enemiesLDX #$00Runs the eleven enemy slots (5-15, X = 0-10 here, so the fields read $0412, $0422, $0432 ... for slot X + 5) on every pass of the game logic ($08F7), which misses the frame on which the map moves a whole row. First zeroes the count of gate soldiers alive ($04F4)…
$24978E F4 04STX gate_alive
$249ABD 32 04b_249ALDA enemy_y,X
$249DC9 1ECMP #$1E
$54E800 07 0Evoice_regs.byteThe SID register offset of each voice: 0, 7, 14.

Coverage: how much is explained

Coverage counts the bytes whose routine, table or variable has a description in words. At 100 %, nothing in the program is left bare: every routine is named and described, and so is every table. A Bronze game stops short of 100 %, and a Silver game reaches it.

Coverage says nothing about whether the descriptions are right. A comment that names the wrong caller counts the same as one that names the right one. That is what the second row measures.

What a wrong comment looks like

Comments are rarely wrong about what a routine is for. They are wrong in a detail, and the wrong detail reads as plausibly as the rest. Each of these came up in a sample of a C64 listing on the site, was found by an agent that had not written it, and has been corrected.

When it runs
Commando · $2495 update_enemies

the enemies run every frame.

they run on every pass of the game logic, which skips the frame on which the map moves a whole row. Fifteen other comments made the same claim.

A count
Spy vs Spy · $885D plane_takeoff

the engine’s pitch rises for the first 60 of the plane’s 160 steps.

it rises for 61.

Most rows, not all
Spy vs Spy · $0914 furniture_rec_lo

the high bytes at $0925 are all $09.

the table is 00 09 09 09 …: type 0’s is $00.

Which is which
Spy vs Spy · $1B26 and $1B29

each of the two weight tables was described as the other.

the game reads them the other way round.

Units
Armalyte · the level decoder

rates in frames.

the main loop moves the paths and the animation on alternate frames ($68), so those rates are in pairs of frames. Eight of the 20 decoder comments in the sample had it.

A template
Wasteland · the map decoder

a square’s tests run when the party arrives.

with bit 7 of its flags clear they run on a move onto the square, and with bit 6 clear only on a Use. The audit rewrote 2,017 of the decoder’s 7,973 comments.

In Bubble Bobble’s three samples, no comment got wrong which routine, table or variable it described. That is why these errors survive. A reader who knows what the routine is for finds nothing odd, and neither does the agent that wrote it.

A program that writes comments, such as a decoder that describes every level, makes one claim hundreds of times. When its sentence is wrong, hundreds of comments are wrong together, so a sample gives those comments a stratum of their own.

Sampling: measuring without checking everything

A listing holds hundreds or thousands of comments. A sample measures the whole listing from a few of its comments:

  1. Draw about 60 comments at random, with a fixed seed. The seed is a number that makes the draw repeatable, so anyone can draw the same 60 again.
  2. Give them to a checker: an agent that wrote none of them, with the kit’s checker brief. The brief lists the kinds of error above and how to test each one. It says to search for every caller, work out every figure, and run the routine when a comment says what it does.
  3. The checker marks each comment right, wrong in a detail, wrong, doubtful or unverifiable, with its evidence. The run then reads every comment marked wrong or doubtful against the code itself, and drops the false alarms.
  4. The number of comments still wrong, out of the number drawn, is the measure.

A count from 60 comments is not exact. Two wrong in 60 could come from a listing with 1 % of its comments wrong, or one with 11 %. The calculator gives that range: the share of the whole listing that is likely wrong, given what the sample found. The page’s row is made the same way.

The mark: 2 in 60

A sample is within the mark when at most 2 of its 60 comments are wrong, or one in 30 in a larger sample. The mark lets a listing with few errors through most of the time, and almost never a first draft.

First drafts are not close. Of the 17 games with a first sample on record on 11 October 2026, 16 had more than 2 wrong in 60, typically one comment in eight. Commando’s first sample had 12 of 70 wrong, Spy vs Spy’s 12 of 60, and Lode Runner’s 17 of 60.

Audits: checking every comment

Correcting the comments a sample found wrong does not correct the listing, because the sample’s rate holds across the comments it did not draw. Bubble Bobble’s first sample had 11 of 60 wrong. Those were rewritten, along with others like them, and a fresh sample still had 10 of 60.

An audit checks every comment. Fresh agents that wrote none of them take one range of the listing each, with the same checker brief and the kinds of error the sample found, and correct what they find. Then a new sample, with a new seed and a checker that neither wrote nor audited any of it, measures the result. Commando went through each step:

  • First sample70 comments drawn, 12 wrong: between 10 and 28 % of the listing. Among the errors were a frame count given for a random chance, a caller list too broad, one sprite block taken for another, two counts off by one frame, and four map descriptions with a row or a terrain class wrong.
  • AuditFour agents checked all 897 comments, a range each, and corrected 137 of them (15 %). The errors were of the same kinds.
  • Second sample70 more drawn, 1 wrong: between 0 and 8 %. That one was the “every frame” above, and the 15 other comments that made the same claim were corrected with it.

After an audit, the next sample was within the mark in 4 of the 7 games that drew one, and a fifth missed it by one comment.

One wrong belief is often written down many times: Commando’s “every frame” was in 16 comments. So when a checker finds a wrong comment, the run searches the listing for every other comment that says the same, and corrects them together.

An audit reads every comment again, so it costs a large share of a run. A contributor on a tight usage limit can stop after the first sample and publish. The page then says the listing has not been audited, until a later run does it.

Checkers: a sample sees what its checker sees

A checker finds only what its model can see. On a test of 60 comments with 20 errors already known (11 October 2026), Claude models found:

CheckerOf the 20 errors, found
Opus16 to 18, and 18 with the kit’s brief

Haiku4 to 7

Opus raised no false alarm, and Haiku raised some. A GPT model found three errors that every run on a Claude model had passed. A comment is wrong when either checker’s finding holds, so a second provider’s model is worth running when the contributor has one.

So the About tab names the model behind every step. Use the strongest model you have to check, and read even the strongest one’s count as a floor: in one full audit, the auditors found 6 wrong comments among the 53 a strong checker had passed in the sample before it.

The ledger: every step, in order

Games do not all go through the same steps. One run samples twice before it audits; another audits only the routines; a third builds a Play tab that corrects comments along the way. So the About tab does not grade a game against a fixed sequence. It lists every step that measured the listing’s comments or made them more accurate, in the order they happened, with the models that did each, and the reader judges how much work stands behind the listing. Each kind of row:

Research
Whether the run looked the game up online (its manual, reviews, wiki pages) before reading its code. A run that knows what the game does names its routines better, so it is worth recording; where nobody wrote it down, the row says so.
Annotation
A run that wrote the comments. A second model, or a second pass that rewrote them, is a row of its own. The last one carries the coverage and how many comments the listing holds.
Sample
A random draw of comments, checked one by one by an agent that wrote none of them. Two samples in a row are two rows.
Audit
Every comment checked, or a stated part of them: an audit that covered only the routines says how many of how many, and one nobody counted says what it covered.
Play tab
A port of the whole game to JavaScript, checked against the game’s own code or its demonstration until the two agree. Porting a routine means reading every instruction of it, so the port finds comments that are wrong, and the row says how many it corrected. Bubble Bobble’s port corrected 16.
Maintainer’s check
A maintainer testing a sample of the run’s claims against the game, for a run made on a model the site does not yet trust (below). A check that failed is a row too, before the work that was redone.

Only samples and full audits change the “Comments checked” row. A Play tab’s port reads only the code it needs, and a maintainer’s check tests the run’s facts and names rather than a random draw of comments, so both add to the record without changing the verdict.

The maintainer’s check

Any model may run the kit, but only a proven model can take a game to Silver on its own. A model is proven once it has taken a game to Silver, or when the maintainers list it as good enough in the kit’s models.json. When a run’s annotation (coverage) or verification ran on any other model, or the game was built on an analysis made with one, the game stays at Bronze until a maintainer has checked it.

The check exists because a weaker model’s mistakes are silent. Its wrong claims read as confidently as its right ones, so reading the page finds nothing. The maintainer, or their agent on a proven model (never the model that made the run), picks the sample:

  • twenty claims from the game’s facts, preferring the ones the page leans on and anything with a number in it;
  • ten named routines or tables, spread across the program;
  • the orientation: where the program loads, where its main loop is, and how memory is set up during play.

Each is traced in the listing, and claims about behaviour are watched in the emulator. One wrong claim fails the check, since a sample that finds one error means there are others. The run is then fixed, verified again, and checked with a fresh sample. The one check on record by 12 October 2026 failed first, with 18 of 39 claims wrong, and passed with none wrong after a proven model redid the work.

It is a different test from a sample. A sample measures how many of the listing’s comments are wrong and has a mark of one in 30. The check asks whether the run can be trusted at all and has a mark of zero.

Reading the row

The “Comments checked” row sums the ledger up from its last sample and the full audits around it. At Silver and above, until the listing has had a full audit and a later sample within the mark, the banner under the game’s title also says so, on every tab. These examples use Commando’s numbers and others made up for the purpose.

Checked. Every comment was audited once, then the last sample of 70 comments had 1 wrong, so between 0 and 8 % of the listing’s comments are likely wrong. No line in the banner.
Not audited. No audit has checked every comment, and the last sample of 70 comments had 12 wrong, so between 10 and 28 % of the listing’s comments are likely wrong. Banner: Its listing has not had a full audit: a sample of 70 of its comments found 12 wrong, about one in 6.
Not checked. Every comment was audited once, but the last sample of 60 comments had 3 wrong, more than one in 30, so between 2 and 14 % of the listing’s comments are likely wrong. Banner: Its listing has been audited, but a later sample of 60 of its comments still found 3 wrong, about one in 20.
Not measured since its audit. The last sample of 60 comments had 9 wrong, so between 8 and 26 % of the listing’s comments are likely wrong; every comment was then audited, and no sample has measured the listing since. Banner: Its listing was audited after its last sample, and no sample has measured it since.
Not measured: no sample of the listing’s comments has been checked. Banner: Nobody has measured how many of its listing’s comments are wrong.

A listing whose first sample is within the mark still reads “Not audited”. The site calls a listing checked only once every comment has been read by an agent that did not write it, and a sample since has measured the result.

Silver needs at least one sample, though not a good one: the ledger shows how much checking went into the listing, and the reader judges it. Games made before 12 October 2026 may be Silver without a sample, and their pages carry the “Not measured” line. When the ledger was first filled in, on 12 October 2026, 34 of the 38 Silver and Gold games got a line in their banner.

When is a game understood, and right?

No single number says so. Each check answers one question and leaves others open.

The questionWhat answers itWhat it leaves open
Is any of the program unexplained?Coverage at 100 %Whether the explanations are right
Can the run be trusted at all?A proven model, or a maintainer’s check that passedHow many comments are wrong
Are the listing’s comments right?“Checked”, from a strong checkerWhich comments are wrong; a checker misses some
How much work stands behind them?The ledger on the About tabNothing it does not record
Are the article’s claims right?The Source tab’s notes: every claim traced to the code or seen in the emulatorThe listing’s comments, which have their own measure
Does it describe the game a player knows?Every feature confirmed, traced or marked openDetail below the level of a feature
Has a person read it?Gold: a person has been through every sectionThe comments, unless they read those too
Are the bytes exact?Platinum: the listing reassembles to the original and bootsAnything the comments say

A game is as well understood as the site can show when its coverage is 100 %, its row says “Checked” from a strong checker, its ledger shows the work behind that, and its notes trace every claim. Even then, up to about one comment in 30 may be wrong in a detail. Each page has an Edit link at its foot, so whoever finds one can fix it.

Words used on this page

Listing
Every byte of the program in memory order, with what it is: the Source tab.
Comment
The words on an address in the listing. On a routine’s first address, it describes the whole routine.
Coverage
The share of the program’s bytes whose routine, table or variable has a description.
Sample
About 60 comments drawn at random from the listing, to be checked one by one.
Seed
The number that fixes which comments a sample draws, so the draw can be repeated.
Checker
An agent that wrote none of the comments and checks a sample of them against the code.
Checker brief
The kit’s instructions every checker and auditor works from: the kinds of error, how to test each, and the verdicts.
Wrong in a detail
A comment right about what it describes, with one stated detail wrong: a caller, a count, a unit, a bit.
The mark
At most 2 wrong in a sample of 60, or one in 30 in a larger one.
Audit
Agents that wrote none of the comments check every one, each in its own range, and correct what they find.
Range
The share of the whole listing likely wrong, given the sample: wide for a small sample, 95 % confidence.
Checked
The listing had a full audit, and a sample after it was within the mark.
Ledger
The About tab’s table of every step that measured the comments or made them more accurate, in order, with the models that did each.
Play tab port
The whole game rewritten in JavaScript and checked against the game itself until the two agree; the comments it shows wrong are corrected and counted.
Proven model
A model that has taken a game to Silver, or that the maintainers list as good enough.
Maintainer’s check
A maintainer’s test of a sample of a run’s claims (twenty facts, ten names and the orientation) against the game, needed when the run used a model that is not proven. One wrong claim fails it.
