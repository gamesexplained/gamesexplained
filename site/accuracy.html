How listings are checked

Accuracy of the Source

Every game on this site has a Source tab: the game’s program, with comments saying what each part does. This page explains how the site measures two things about those comments: how much of the program they cover, and how many of them are right. The examples come from C64 games on the site.

The listing

The Source tab shows the game’s listing. A listing is the whole program, byte by byte, in the order it sits in memory. Code appears as instructions, and tables and variables appear as bytes. A routine or a table starts with a name and a comment, and the comment says what the whole routine or table does. Every byte up to the next name belongs to it.

$2495A2 00update_enemiesLDX #$00Runs the eleven enemy slots (5-15, X = 0-10 here, so the fields read $0412, $0422, $0432 ... for slot X + 5) on every pass of the game logic ($08F7), which misses the frame on which the map moves a whole row. First zeroes the count of gate soldiers alive ($04F4)…
$24978E F4 04STX gate_alive
$249ABD 32 04b_249ALDA enemy_y,X
$249DC9 1ECMP #$1E
$54E800 07 0Evoice_regs.byteThe SID register offset of each voice: 0, 7, 14.

Coverage: how much is explained

Coverage is the share of the program’s bytes that belong to a routine, table or variable with a description. At 100 %, every routine and every table has a name and a description. A Bronze game is below 100 %, and a Silver game is at 100 %.

Coverage counts comments. It can’t tell a right comment from a wrong one, so a comment with a mistake in it counts the same as a correct one. The second row, “Comments checked”, measures how many are right.

What a wrong comment looks like

A wrong comment usually gets the big picture right: it knows what the routine is for. The mistake is in one detail, such as a count, a unit, or which routine calls it, and that detail sounds as believable as the rest. Each mistake below was found in a C64 listing on this site by an agent that hadn’t written it, and each has since been fixed.

When it runs
Commando · $2495 update_enemies

the enemies run every frame.

they run once per pass of the game logic, and the game logic skips the frame where the map scrolls by a whole row. Fifteen other comments made the same mistake.

A count
Spy vs Spy · $885D plane_takeoff

the engine’s pitch rises for the first 60 of the plane’s 160 steps.

it rises for 61.

One odd row
Spy vs Spy · $0914 furniture_rec_lo

the high bytes at $0925 are all $09.

the table starts 00 09 09 09 …, so the first one, for type 0, is $00.

Two things swapped
Spy vs Spy · $1B26 and $1B29

a description of each weight table that fits the other one.

swap the two descriptions and both are right.

Units
Armalyte · the level decoder

the rates are counted in frames.

the main loop moves the paths and the animation on every other frame ($68), so the rates are counted in pairs of frames. Eight of the 20 decoder comments in the sample had this mistake.

One sentence, many comments
Wasteland · the map decoder

a square’s tests run when the party arrives.

two bits of the square’s flags decide. With bit 7 clear, the tests run when the party steps onto the square. With bit 6 clear, they run only when the player chooses Use. The audit rewrote 2,017 of the decoder’s 7,973 comments.

In Bubble Bobble’s three samples, every comment named the right routine, table or variable. All of the mistakes were in details. That is why mistakes like these last: a reader who knows what the routine is for sees nothing strange, and neither does the agent that wrote it.

Some comments are written by a small program rather than one at a time. A decoder, for example, writes a description of every level from one sentence pattern. When that sentence is wrong, hundreds of comments are wrong at once. So a sample treats those comments as a group of their own and always draws some of them.

Sampling: checking a few to measure them all

A listing has hundreds or thousands of comments, and checking every one takes a long time. A sample checks a few of them and uses the result to estimate the rest:

  1. Pick about 60 comments at random. A number called the seed decides which ones, so anyone can pick the same 60 again.
  2. Give them to a checker. A checker is an AI agent that wrote none of the comments. Checkers do audits too, further down. A checker works from the kit’s checker brief, which lists the kinds of mistake above and how to test for each one: find every place a routine is called from, redo every sum, and run the routine when a comment says what it does.
  3. The checker marks each comment right, wrong, or unsure, shows its evidence, and changes nothing. The run then looks up every comment marked wrong or unsure in the code itself, and throws out the false alarms.
  4. The number of comments still wrong, out of the number picked, is the result.

Sixty comments can’t give an exact answer. If 2 of 60 are wrong, the whole listing might have 1 % of its comments wrong, or it might have 11 %. The calculator shows that range: how much of the whole listing is likely wrong, given what the sample found. The About tab works it out the same way.

Good enough: at most 2 wrong in 60

A sample is good enough when at most 2 of its 60 comments are wrong. A bigger sample is good enough at one wrong in 30. A listing with few mistakes usually gets a good enough sample, and a first draft almost never does.

First drafts are far from good enough. On 11 October 2026, 17 games had a first sample on record, and 16 of them had more than 2 wrong in 60. The usual result was about one comment in eight. Commando’s first sample had 12 of 70 wrong, Spy vs Spy’s had 12 of 60, and Lode Runner’s had 17 of 60.

Audits: checking every comment

Fixing the comments a sample found wrong leaves the rest of the listing as it was. The sample looked at only 60 comments, and the others have mistakes at about the same rate. Bubble Bobble’s first sample had 11 of 60 wrong. Those were fixed, along with others like them, and the next sample still had 10 of 60 wrong.

An audit checks every comment. New checkers, which wrote none of the comments, each take one part of the listing. They use the same brief, plus the kinds of mistake the sample found, and this time they fix what they find. Then a new sample measures the result, with a new seed and a checker that took no part in the writing or the audit. Commando went through each step:

  • First sample70 comments picked, 12 wrong, so between 10 and 28 % of the listing was likely wrong. The mistakes included a random chance described as a number of frames, a list of callers that named too many, one sprite block mistaken for another, two counts off by one frame, and four map descriptions with a row or a type of ground wrong.
  • AuditFour checkers went through all 897 comments, one part each, and fixed 137 of them (15 %). The mistakes were of the same kinds.
  • Second sample70 more picked, 1 wrong, so between 0 and 8 %. That one was the “every frame” mistake above, and the 15 other comments that said the same thing were fixed with it.

After an audit, the next sample was good enough in 4 of the 7 games that took one, and a fifth missed by one comment.

The same wrong idea often turns up in many comments: Commando’s “every frame” was in 16 of them. So when a checker finds a wrong comment, the run searches the whole listing for others that say the same thing, and fixes them all together.

An audit reads every comment again, so it takes a large part of a run. A game’s first run doesn’t do one: it takes one sample, fixes what the sample found, and publishes. Most of what a page is worth comes from explaining the whole program, and the sample tells readers how far to trust the comments. The Source tab then says the listing hasn’t had a full audit, and the run recommends one for a later run to do when someone asks.

Checkers: a sample is only as good as its checker

A checker finds only the mistakes its model is able to see. On 11 October 2026, Claude models were tested on 60 comments that held 20 known mistakes. They found:

CheckerMistakes found, of 20
Opus16 to 18, and 18 with the kit’s brief
Fableabout 12
Sonnet10 to 12
Haiku4 to 7

Opus raised no false alarms, and Haiku raised a few. A GPT model found three mistakes that every Claude run had missed. A comment counts as wrong when either checker’s finding holds up, so a second checker from another company is worth running when the contributor has one.

A weak checker makes a listing look better than it is, because the mistakes it misses count as right. Set how many of a listing’s comments are actually wrong, and see how many of them each checker finds in a sample of 60, and whether it then calls the listing good enough.

What each checker finds in a sample of 60

Each bar is how many wrong comments the checker finds in a sample of 60, on average, if it finds the middle of its range in the table above. The dashed line is good enough: 2 or fewer. The verdict is green when it is the right answer and red when it is the wrong one.

That is why the About tab names the model behind every step. Check with the strongest model you have. Even then, the real number of mistakes is probably higher than its count: in one full audit, the checkers found 6 wrong comments among 53 that a strong checker had passed in the sample just before.

The ledger: every step, in order

Games go through different steps. One run samples twice before its audit. Another audits only the routines. A third builds a Play tab, which fixes comments along the way. So the About tab lists every step that measured the comments or made them more accurate, in the order they happened, with the models that did each one. You can see how much work went into the listing and judge it for yourself. Commando’s ledger:

Each kind of row:

Research
Whether the run looked the game up online (its manual, reviews, or wiki pages) before reading its code. A run that knows what the game does gives its routines better names.
Annotation
A run that wrote the comments. When a second model or a second pass rewrote them, that is another row. The last one shows the coverage and how many comments the listing has.
Sample
About 60 comments picked at random and checked one at a time by a checker. The row says how many were wrong and whether they were then corrected. Two samples in a row are two rows.
Audit
Every comment checked, or a stated part of them. A partial audit says how many it checked, or what it covered when nobody counted.
Play tab
The whole game rewritten in JavaScript and tested against the real game until the two match. Rewriting a routine means reading every instruction in it, so the port turns up wrong comments, and the row says how many it fixed. Bubble Bobble’s port fixed 16.
A name in the By column
A maintainer made this sample or audit, for a run made on a model the site doesn’t trust yet (see the next section).
Maintainer’s check
The older form of that check, from before 12 October 2026: about 40 of the run’s claims tested against the game. One game on the site has these rows.

Only samples and full audits change the “Comments checked” row. A Play tab’s port reads only the code it needs, and the older maintainer’s check tested the game’s notes and names, so both of them leave the row as it is.

The maintainer’s check

Any AI model can run the kit, and a proven model can take a game to Silver on its own. A model is proven when the site’s maintainers have listed it as good enough, or when it took a game to Silver early on, before this check existed. When any other model wrote or checked a game’s comments, the game stays at Bronze until a maintainer has checked it. Its page is still published in full, and its banner says it is waiting for the check.

The check is needed because a weaker model’s mistakes look as confident as its correct work, and because it is a weaker checker too. When it samples its own listing, it misses more of its own mistakes: in the test above, Haiku found 4 to 7 of the 20, and Opus found 16 to 18. So a run’s own sample can make its listing look better than it is.

The maintainer, or their agent on a proven model, does the same measuring every run does:

  1. Sample 60 comments, with a seed the maintainer picks.
  2. When more than 2 of the 60 are wrong, audit every comment, and every claim in the game’s notes, which the How it works article is built on. Fix what is wrong.
  3. After an audit, sample again with a new seed.

These steps go in the ledger as ordinary sample and audit rows, with the maintainer’s name in the By column. The page then shows the maintainer’s result, good enough or not. A model becomes proven only when the maintainers add it to their list, once its work has measured well.

Until 12 October 2026, the check worked differently: a maintainer tested about 40 of the run’s claims, and one mistake failed the whole run. Every listing has some mistakes, though, even a good one. At 5 % wrong, a test of 40 claims comes back with zero mistakes about one time in seven, so the old check failed most good runs as well as the bad ones.

Reading the row

The “Comments checked” row sums up the ledger, using the last sample and any full audits around it. At Silver and above, the Source tab shows the same verdict in a line under its title, with a shorter sentence on why and a link to the ledger. A listing whose first sample is good enough still says “Not audited”. The site says “Audited & low error rate” only once two things have happened: an agent that didn’t write the comments has read every one of them, and a later sample has measured the result.

Silver needs at least one sample, and the sample may show any result. The ledger shows how much checking went into the listing, and the reader judges it. Games made before 12 October 2026 can be Silver with no sample at all, and their pages show the “Not measured” line. When the ledger was first filled in, on 12 October 2026, 4 of the 38 Silver and Gold games had “Audited & low error rate”.

When is a game understood, and right?

No single number says so. Each check answers one question and leaves others open.

The questionWhat answers itWhat it leaves open
Is every part of the program explained?Coverage at 100 %Whether the explanations are right
Can the measuring be trusted?A proven model did it, or a maintainer did it again on oneThe result, which the row shows
Are the listing’s comments right?“Audited & low error rate”, from a strong checkerWhich ones are wrong: even a strong checker misses some
How much work went into them?The ledger on the About tabAny step nobody recorded
Are the article’s claims right?The Source tab’s notes: every claim traced to the code or seen running in the emulatorThe listing’s comments, which are measured on their own
Does it describe the game a player knows?Every feature confirmed, traced, or marked openDetails smaller than a feature
Has a person read it?Gold: a person has been through every sectionThe comments, unless they read those too
Are the bytes exact?Platinum: the listing turns back into the original program, and it runsWhether the comments are right

A game is as well understood as the site can show when its coverage is 100 %, its row says “Audited & low error rate” from a strong checker, its ledger shows the work behind that, and its notes trace every claim. Even then, up to about one comment in 30 may have a wrong detail. Every page has an Edit link at the bottom, so anyone who finds one can fix it.

Words used on this page

Listing
The whole program, byte by byte, in memory order, with what each part is. It is the Source tab.
Comment
The words beside an address in the listing. On the first address of a routine, the comment describes the whole routine.
Coverage
The share of the program’s bytes that belong to something with a description.
Sample
About 60 comments picked at random from the listing and checked one at a time by a checker, which changes nothing.
Seed
The number that decides which comments a sample picks, so the same pick can be made again.
Checker
An agent that wrote none of the comments and checks them against the code. It does two jobs: a sample, where it marks about 60 comments and changes nothing, and an audit, where it checks every comment in its part of the listing and fixes the wrong ones. A checker on a sample took no part in the writing or in an audit before it.
Checker brief
The kit’s instructions for every checker, on a sample or an audit: the kinds of mistake, how to test for each, and how to mark the result.
Wrong in a detail
A comment that is right about what it describes, with one fact wrong: a caller, a count, a unit, or a bit.
Good enough
At most 2 wrong in a sample of 60, or one in 30 in a bigger sample.
Audit
Checkers go through every comment, each in its own part of the listing, and fix what they find.
Range
How much of the whole listing is likely wrong, given the sample, at 95 % confidence. A small sample gives a wide range.
Audited & low error rate
The listing had a full audit, and a sample after it was good enough.
Ledger
The About tab’s table of every step that measured the comments or made them more accurate, in order, with the models that did each one.
Play tab port
The whole game rewritten in JavaScript and tested against the real game until the two match. The wrong comments it turns up are fixed and counted.
Proven model
A model the maintainers have listed as good enough, or one that took a game to Silver before the maintainer’s check existed.
Maintainer’s check
For a game made on a model that isn’t proven: a maintainer samples its listing on a proven model, and audits it when more than 2 of the 60 are wrong.
