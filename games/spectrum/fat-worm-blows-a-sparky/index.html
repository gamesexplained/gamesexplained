ZX Spectrum · 1986 · Durell Software

Fat Worm Blows a Sparky

A worm crawls across the inside of a ZX Spectrum, and the board is drawn block by block in a perspective that never stops moving.

01 · The view

The screen, rebuilt from the game's own memory

A reconstruction, not a screenshot. The page holds the 6912 bytes of video memory the game wrote and draws them with the ULA's own rules.

One frame of play. The worm is the small chevron at the centre. The board is green; the HUD along the bottom carries the insert map, a status bar, and the counters for sparkies, spindles and score. Drawn from $4000-$5AFF in the play snapshot.

The picture is two arrays. $4000-$57FF is one bit per pixel, but the 192 lines are stored a third of the screen at a time, so the address of a pixel swaps the top two bits of its row for the low three. $5800-$5AFF is one attribute byte per 8×8 cell, holding ink, paper, brightness and flash. Read together they give the picture, with no emulator in the loop.

02 · Perspective

The scale is a single multiply

Every object on the board is drawn twice, at two sizes the game takes from one curve. The board stays flat under the worm and widens towards the edge of the screen.

Drag the slider. The index walks the 64-byte curve at $6300; the value it returns is the multiplier used by the routine at $811E, extent × (128+B) ÷ 128. At the centre the factor is 1, so blocks show only their tops. Towards the edge the factor grows and their sides come into view.

$80EB reads the curve with B = curve[A >> 1] and applies it to each of an object's four extent words through the shift-and-add at $811E. That routine is also the game's only range test: a coordinate whose magnitude is 192 or more comes back unchanged, which is how things outside the view pass through untouched.

04 · The board

A circuit board the size of a room

The whole board. A fan map from the Spectrum Computing archive. Blocks, ramps, data buses and the disk drive the worm has to reach are laid out on it. The game draws a small insert of the nearby cells into the bottom-left of the screen.

The board's own data lives at $5B00-$757E. Each cell's script is an 8-byte record; the walker at $AF49 takes the two bytes behind a tag byte as the address of the routine that draws that piece of the cell, so the board's layout and its graphics are the same block of bytes.

05 · Controls

What the game reads

KeyDoes
Qspeed up
Aslow down
Orotate left
Protate right
1drop a burper sparky
SPACEfire a blaster sparky
Hhalt: runs the bouncing-ball screen
Ggive up and return to the menu

Keys are redefinable; a Kempston joystick is read from port $1F. The keyboard rows come in through the ULA at $FE, the only input port the game uses.

06 · Boot

A £100 reward before the game

The first thing you see. The game draws this warning from a text table at $7CE0, then waits for a key. After the key it copies a pre-rendered picture from $F000 into the screen and shows the menu.

07 · Bug

The draw list that starts empty on purpose

One frame's list of things to draw is built fresh each pass. The first two instructions to build it look like a mistake, and the game works because of it.

AAF3  21 8D EB   ld hl,$EB8D     ; the head of last frame's list
AAF6  21 00 00   ld hl,$0000     ; ...immediately overwritten
AAF9  22 7E EB   ld ($EB7E),hl   ; store the null head
AAFC  AF         xor a
AAFD  77         ld (hl),a       ; writes to $0000, in the ROM

The two instructions cancel out: the list is emptied to a null pointer, and the byte written through it lands on $0000 where it cannot do anything. The result is a correct empty list built from a load that never takes effect.
