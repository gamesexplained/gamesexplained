The game is a Z80 program of 22,521 bytes, the engine, and five scenarios of 18,911 bytes each, loaded from tape over the top of memory, each with routines of its own and its own copy of the computer player. The port is the same program written again in JavaScript: one function for each of the engine's 289 routines and for the 40 routines the scenarios carry, in 144 copies, each reading and writing the game's variables at the game's own addresses. The page runs only the port. The game's code is in the tests, as the original the port is held to.

CheckWhat it showed
Each routine aloneThe 201 routines that run to their end without waiting for a key, a delay or the tape are each taken at the moments the game itself calls them, from moments of play saved from the emulator, up to 60 moments a routine: 8,476 in all. The port's routine and the game's own, on the kit's Z80, start from the same machine, and all of memory, the writes to the screen's border and the beeper, and the registers the routine hands back must come out the same. All 8,476 did.
The whole program in lockstepThe port's program runs beside the game's, from the engine's first instruction through the menus, the tape, the shop and the placing of the units into the turns, with a player at random answering every read of the keys: two-player games in all five scenarios, games against the computer at each of its seven levels, and games with each of the four kinds of controls. Over 108,500 passes of the main loop in 25 games, every byte of memory was the same at every read of the controls, but for the stack. The routines that wait, and the few the saved moments never reach, such as the blasts, are held to the game here.
The random numbersThe game's dice add the Z80's refresh register, which no port can keep, a byte read from a pointer that walks the whole of memory, and the time spent waiting for keys. In the tests both sides read the same made-up values for the register, in the order they read them, so a port that read it once too often or too seldom would be out of step at once; on the page it is noise.
The page's memoryThe page carries the game's memory as the tape leaves it with every byte of an instruction set to zero: 17,288 bytes of the engine and from 2,766 to 3,276 of each scenario. It keeps the hooks at the head of each scenario, which the port follows, and the few bytes of code the port reads. The page's machine on that memory played a two-player game of Moonbase Assault and a game of Paradise Valley against the computer beside the port on the whole memory, and the two were the same at every read of the controls. A game the page saved there loads again from the first menu and goes on.
The paceThe game runs with the interrupts off and paces itself with delay loops, so the page runs the port's delays, sounds and tape for the T-states the game spends on them, and charges every other stretch of the program, each routine and each piece of work counted inside them the T-states they cost the game. Those costs are fitted on 89,480 passes timed on the kit's model of the 48K, the many short stretches of the menus and the cursor weighted as heavily as the long ones of the computer's turns. On five games it was not fitted on, of 18,995 passes in all, each whole game takes within 0.8 % of the game's time and the middle pass within 0.5 %. On the page's own machine, the two-player game above took 0.3 % less than the game's time and the game against the computer 0.5 % more, with half their passes within 3.1 % and 2.0 % of the game's.
