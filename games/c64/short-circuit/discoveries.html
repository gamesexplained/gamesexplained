Things the code does that the manual and the wiki do not say.

01 · A key to jump straight to part two

A key to jump straight to part two

On the attract screens, F3 starts part two at once, with the clock at 6:00 and no part one played; F1 starts part one without the intro ($95B5, $95BF). The C64-Wiki page says only that cracked copies with a menu skip to part two. Here the original code does it, so no crack is needed. Seen live: with F3 pressed the countryside came up with the clock at 6:00.

02 · The boot program starts itself by loading

The boot program starts itself by loading

The cassette's first file, in the KERNAL's own format, loads at $0316: on top of the KERNAL's table of vectors, the addresses the system jumps through for its input and output. Nine of the vectors it brings, among them the one for printing a character at $0326, point at $0363, the boot program's own first instruction. So no SYS is needed: the first time the system reaches for one of those routines after the load, it runs the loader instead. Two more, the BRK and NMI vectors at $0316 and $0318, point at $EA86, an RTI in the KERNAL, so the RESTORE key does nothing while the tape loads.

03 · Collisions are done in software

Collisions are done in software

The census of the chip registers finds no read of the sprite collision registers $D01E and $D01F. Every touch, whether Johnny against the enemy robot ($1BD5) or against a creature of part two ($2DD4 on), is a subtraction of sprite positions.

04 · The clock is real time, and F7 stops it

The clock is real time, and F7 stops it

The thirty minutes of part one are counted by the second CIA chip's time-of-day clock, not by frames. The pause key freezes it by reading the hours register, which latches the clock, and writing it back, then restores the tenths register to start it again ($21CF). Seen live: the clock read the same value three seconds apart while paused.

05 · Undocumented opcodes in the colour fill

Undocumented opcodes in the colour fill

Seven loops ($0BCF, $0BDD, $1EC8, $1ED6, $2AD6, $2AF4, $2B02) read a character from the screen with the opcode $B3, LAX (zp),y, which loads A and X together so that the next instruction can use X to look up the character's colour. A disassembler that does not know the opcode shows a stray byte and then garbage instructions.

06 · An older build left in the file

An older build left in the file

The 544 bytes at $3DE0 to $3FFF are the code from $39C4 to $3BE3 (the end of the sinking animation through the trigger that starts a chaser) as it stood in an earlier build, $41C bytes further on. It uses the same variables as the live code, but its calls go to where routines used to be: it calls $1F87 where the live code calls $1EE4. Nothing refers to it and no run executes it.

07 · Three tempos for one driver

Three tempos for one driver

The same Galway driver is called at three rates: once a frame in part one, 3.5 times a frame by the attract mode (four handlers, each adding $E4 to a counter and ticking on the carry) and about 2.75 times in part two. The Music tab does the same for each tune.

08 · Spelling and a scrambled heading

Spelling and a scrambled heading

The game's text spells achieved as ACHEIVED (message 33 and the description of the computer protocols) and overridden as OVERIDED (message 34). Message 49, the copyright message, ends with the letters RAPT OEN, an anagram of PART ONE, just before the heading PART ONE; what the scramble is for was not found.

09 · The credits hide behind the title picture

The credits hide behind the title picture

The 1,192 bytes after the title picture's bitmap, $7F40 to $83E7, looked unread: no instruction names them. They are the credits screen. $9637 switches the video chip to bank 2 with $D018 = $02, which puts its screen at $8000 and its characters at $8800, so $8000-$83E7 is the credits' screen and $8C00-$8F8F the shapes of the logo and the names (Graphics). What is left, $7F40-$7FFF, is a second copy of a stretch of the message text, from the end of message 75 to the start of message 83, which nothing reads.

10 · Event 10

A creature that never comes

Part two's table of creature starters at $8A6E has sixteen entries for the event numbers 0 to 15. Entry 0 is empty because 0 means nothing happens. Entry 10 is empty as well, and none of the 256 columns of the event table at $896E holds a 10, so the gap is never reached. What event 10 was meant to be, the code does not say.

11 · One key, three drawers

One key, three drawers

Two tables list the laboratory's locked drawers and cabinets, and they disagree about one of them. The table of containers at $15BC has a drawer at map column $9D; the table of places where INPUT does something, at $15CC, has the same drawer at $9A. The map sides with the second: the tile at $9D is not one of the 43 that SEARCH and UTILISE accept, and the one at $9A is.

So the drawer is at $9A, and putting the DESK KEY into it runs the lock check at $1CFA for a column the container table does not hold. The check has no end test: it reads on past the eight columns, through the table of bit masks and into the INPUT table, until it meets a byte $9A at $15D8, 28 bytes in. It then takes the drawer's bit from 28 bytes into the masks, the byte $1C, and sets three bits at once in the open flags at $020B: the drawers at $8F, $9D and $E3 are all open. All three take the DESK KEY anyway, so a player saves two trips; the drawer at $9D, which cannot be searched, is opened without ever being seen. Checked by running the game's own INPUT step ($183D) on the kit's 6502 from a snapshot of part one, with Johnny at each column and the DESK KEY chosen: at $9A the open flags went from %00000000 to %00011100, at $8F to %00000100, and at $9D INPUT found no entry.
