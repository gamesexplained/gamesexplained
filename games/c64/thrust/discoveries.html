1986 · Firebird

Thrust

What the program holds that a player never sees: the BBC Micro version's key page, calls to a music player that is not there, code that can never run, and three sprites nobody draws.

01 · The BBC Micro's key page

Secret: the C64 game carries the BBC Micro's instructions page

Thrust began on the BBC Micro, written by Jeremy C. Smith. The C64 program still holds the BBC version's key page, in the BBC's own teletext codes.

The text at $B9DD, drawn by this page the way the BBC Micro's MODE 7 would show it: each control code takes a cell and changes the colour, the background or the height of what follows.

The text opens with the bytes 22 and 7, which the BBC Micro reads as "change to MODE 7", its teletext screen. After them come teletext control codes: $84 blue, $9D new background, $83 yellow, $8D double height. The keys it lists are the BBC's: CAPS LOCK and CTRL to turn, COPY and DELETE to freeze, ESCAPE to quit. The C64 version uses A and S, the function keys and RUN/STOP.

The crackers added their own line near the end, "Cracked By The Syndicate For TCI !", in letters with the top bit set, which teletext shows as plain capitals. A routine to print the page is there too: show_bbc_keys_page ($B74B) sends the text to the C64's own print routine (CHROUT), waits for Space and starts the game. No instruction calls it, and no table holds its address. On a C64 the teletext codes would print as other characters, so the page could never have looked like this one.

02 · The missing music

Secret: the calls to the music player land on an RTS

Thrust on the C64 is known for Rob Hubbard's music. This copy has none, but the calls to play it are still in the code.

CallFromWhat is there
JSR $3000, every frameraster_handler_0, $8A38$60, an RTS: the first byte of the program's old copy, left at $3000 by the relocator
JSR $A951 with 7 and 1 in A and Yrestart_ship, $A699an RTS (music_hook)
JSR $A951 with 0 and 0restart_ship, clear_play_area, life_statethe same RTS

No instruction in the snapshot, at the hand-over or in play, writes to the sound chip at $D400-$D41C: a search for every store instruction with those addresses finds none. The only writes to the chip are the sound effects', through its mirror at $D500.

A call every frame and a call with a tune number at the start and end of each life is how a music player is usually driven. Here the per-frame call goes to $3000. The relocator copied the program from $3000 up to $8280 and left the old copy behind. Its first byte, $60, happens to be an RTS, so the call returns at once. The sound effects use the chip's mirror at $D500 rather than $D400. Whether Firebird's release played music through these calls is not something this copy can show.

03 · Straight into a game

Secret: this copy starts a game the moment it loads

After the loading picture, the first thing on screen is a game, with three lives and nobody at the controls.

The start-up code ($B773, run at $0400) ends with a jump to $AF82, seven bytes after pen_diagonal that only this jump reaches. They turn the sound on, then jump to start_game ($B044). The title, with its high score table and the demo pilot, is title ($AF93), and it comes up only when a game ends. In the emulator, with no key pressed, the ship fell and was lost three times. After about 35 seconds the high score table appeared, and the demo pilot took over. Whether TCI added that jump is not known.

04 · Code that can never run

Bug: a random choice that the branch before it skips

free_shot_slot ($9FDD) finds a slot for a new shot or piece of debris. If every slot is busy, the code after the search would pick one at random, but nothing can reach it.

$9FF7  beq $A003     ; return if Y is 0
$9FF9  bne $9FF7     ; otherwise branch back to the BEQ above
$9FFB  jsr random    ; never reached
$9FFE  and #$0F
$A000  adc #$04
$A002  tay

The end of free_shot_slot. Whichever way the zero flag is set, the two branches end at the RTS at $A003.

The search goes from slot 31 down to slot 1, first for a free slot and then for one with a short life left. When neither search finds one, Y has counted down to 0, and the BEQ returns with slot 0. That is one of the player's own shot slots. The BNE after it could only loop back to the BEQ, so the random pick of a slot from 4 to 19 at $9FFB never runs. A full table therefore puts a new piece of debris in slot 0.

05 · Leftovers

Routines nothing calls

Two small routines look like tools the programmer used while writing the game.

print_hex ($A004) prints a byte as two hexadecimal digits with the game's own font. It keeps every register it uses, as a routine meant for debugging would. test_shot ($AA8C) puts a shot at a fixed place, with a fixed speed and a life of 40. A references search finds no call or jump to either, and no table holds their addresses.

06 · Unused sprites

Three sprites the game never shows

The sprite data copied to $4000 holds 52 shapes. The game shows 49 of them.

Pointers $31-$33, at $4C40-$4CFF, drawn from the listing's bytes. No sprite pointer the game writes reaches them: its pointers are 0-$30 and the rod's $4C-$4F.

The game sets a sprite's pointer in a few places: the ship's direction or the shield (0-$20), the pod ($21), each object's shapes ($22-$2E), the tractor beam ($2F, $30) and the two buffers the rod is drawn into ($4C-$4F). The three shapes of horizontal lines after them are never used.
