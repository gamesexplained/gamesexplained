Commodore 64 · 1986 · Micro Power

Doctor Who and the Mines of Terror

A 4,096-pixel-wide mine kept under the KERNAL ROM, a robot cat you program in ten steps, and a status bar whose font lives in the unused rows of its own screen.

01 · The screen

One frame, rebuilt from memory

The Doctor, Splinx and the TARDIS at the start of play, drawn by this page from the game's memory and its video registers.

A reconstruction, not a screenshot. One frame recorded in the emulator, every write to the video chip with the line it happened on, drawn line by line. It matches the emulator's own picture in all 104,448 pixels.

The picture is two screens in one. An interrupt at $8010 runs three times a frame and rewrites the video chip each time. From line 256 to line 78 of the next frame the chip shows the status bar out of VIC bank 0, screen $0400. From line 78 it switches to bank 1 and one of two play screens, $7800 or $7C00, which the game draws in turn and swaps while the other is shown. The interrupt keeps the handler's own number in the offset of a branch at $8017, so the next interrupt jumps straight to the next band.

02 · The world

The whole mine, drawn from its map

The mine is one map of 56 rows by 128 blocks, kept in the RAM under the KERNAL ROM at $E000. Drag across the map to move the magnifier.

Every block drawn from map_e000 and the block definitions at $3000, with the play-area characters at $4000 and each character's colour from $2F00. The orange cross is the Doctor's first position. The game swaps in its own shapes for sixteen characters in some zones of the map (zone_graphics); this picture shows every zone with the start zone's, copied from the running game.

A block is four by four characters, sixteen bytes at $3000 + 16 × its number, stored bottom row first. The map holds one byte per block, 128 to a row, and row r starts at $FB80 − 128 × r. Row 0 is the bottom of the mine: the game counts heights upward from the floor, and draws the screen from the bottom row up ($8746). That puts the world at 4,096 by 1,792 pixels in 7 KB.

The game runs with the BASIC and KERNAL ROMs switched out ($01 = $35) from its first instructions to the moment it saves, so all of $A000-$FFFF is RAM for it. The map fills $E000-$FBFF, and the code that plays the TARDIS scenes sits above it, at $FC8C.

Colour RAM holds a colour for every screen cell, and the game never stores one for the map. Each time it draws a row or a column it looks up the colour of each character in a 256-byte table (colour_from_chars, $8EB8), so a character always has the same colour wherever it appears.

03 · The status bar

A font kept in the screen it draws

The status bar is four rows of a 25-row screen. The other 21 rows hold the font the status bar is written in.

In the status band the video chip reads screen $0400 with its character base at $0000. The game writes all its own text in a private alphabet in which a letter is its ASCII code plus 155: A is $DC, Z is $F5, the digits are $F6-$FF and $94 is a space. A character's eight bytes sit at eight times its code, so the glyphs for $94-$FF fill $04A0-$07FF: the rows of the same screen that the band never shows.

The start-up copies the screen and the game's own glyphs from $4B00, then copies A to Z and 0 to 9 from the character ROM into place ($48F5). One glyph does not fit. The glyph for $FF would be the last eight bytes of the screen page, and the video chip reads the eight sprite pointers there. So digit 9 is drawn with code $F5, the letter Z's code, and the digit table at $1730 maps 9 to it. The status bar has no Z to show.

Pockets on the function keys, Splinx on S

Read from the input routine at $8F24, which scans six keyboard rows once a pass and keeps each in its own byte. The BBC Micro version's key list, which is the one found online, does not apply.

The keys D, CTRL+D and L all set the same event byte, $E8, to a negative number, and the event handler at $9102 takes any negative number as "open the save menu". Every pass, though, the Doctor's own update clears that byte unless he stands on character $23 ($C902-$C909). Pressed anywhere else, the keys do nothing.

05 · Splinx

Splinx runs a ten-step program

Splinx follows the Doctor, or runs a program of up to ten commands you write on its own screen.

The programmer screen, $0C00, in screen codes with its own font at $0800. The game parks the play screen's colour RAM at $1000 while it is shown ($B16D).

CommandWhat Splinx does
1-4 GOTO MARKERwalks to one of the four markers the Doctor has dropped
R RETURN TO DOCTORwalks back to him
W WAITstands
P PICK UP OBJECTtakes the nearest free item within 16 × 8 pixels
D DROP OBJECTputs it down

The program is ten bytes at $30-$39, and a mode byte at $FF chooses between shut down, follow the Doctor and execute the program (splinx_update, $B1A0). The interpreter picks a command's handler by writing twice the command number into the offset of a branch at $B1CC; the game uses the same trick for the Doctor, the controllers and most of its creatures.

The battery, $1F, starts full at 24 and loses one unit every 1,024 frames, about 20 seconds, while Splinx follows or runs a program: eight minutes of work from a full charge.

06 · Sprites

144 frames in bank 1

Every hardware sprite image the game keeps, drawn from the bytes at $5000-$73FF. Click one to see its pointer.

Multicolour sprites with the game's shared colours ($D025 = red, $D026 = orange); each object's own colour comes from $1850, and grey stands in for it here.

At most eight objects are on screen at once. Each pass, sprite_list_add_object ($81DA) collects the visible ones and drops any ninth; $8133 writes their frames into the sprite pointers of both play screens. The items with numbers $30-$4F can also be drawn into the background as characters, blended pixel pair by pixel pair into 32 spare character codes ($8652).

09 · Quirks

Bug: a countdown that almost never counts

The time bonus starts at 10,800 and is meant to fall as you play. It falls by one every 21.8 minutes.

The frame routine at $80DA counts frames in three bytes, $53-$55, and was meant to take one off the time bonus every 64 frames. The test that gates it is written after two branches that skip it unless the low two bytes have both just wrapped to zero, which happens once every 65,536 frames. The AND #$3F that should pick every 64th frame then always passes. In practice the whole 10,800 is added to the score at the end.

The first game starts the counter at 010800 in decimal ($4996); every later game, started with F1 after the end, at 010805 ($9408).

Saving ends the game

The save menu writes zero page, the object tables and the status rows into the play screen at $7800, then saves $7800-$7D7F as DRWHO to tape or disc ($94FF). To call the KERNAL it switches the ROMs back in, and when the save is done it jumps through the vector at $A000, which with BASIC in place is BASIC's cold start. The game is gone. Loading the file and starting it again is the only way back: the start-up checks $7800 and restores a saved block if it finds one ($49C6). Nothing in the program itself ever loads.

Exact numbers where a range was meant

The carrier takes the Doctor aboard only when his height is exactly $0450 ($A395), and the lift only when he is exactly eight pixels from its floor ($A294). One pixel either way and he stays where he is.

Two messages exist that nothing prints in the way their text suggests. EXPOSURE TO RADIATION has no entry in the table of death causes. Cause 8, the rising level, points at GAME OVER instead of a cause, so a Doctor who still has lives reads THE DOCTOR REGENERATES AFTER GAME OVER ($90F3).
