01 · The port

Every routine of the game, checked against the original

The game is a 6502 program of about 28,000 bytes of code. The port is the same program written again in JavaScript, one function for each routine the game calls, 123 in all, reading and writing the game's variables at the game's own addresses. The page runs only the port: the game's code is in the tests, as the original the port is held to.

CheckWhat it showed
Each routine aloneFifteen test files call each routine of the port and the game's own routine on the kit's 6502 simulator from the same state, made from saved moments of play with registers, variables and keys changed at random, and compare every byte each one leaves.
The main loop in lockstepThe port's main loop runs beside the game's, pass by pass, from 199 moments: a walk in the Wilderness and every area and entrance the game's scripts lead to, each 150 passes with keys pressed at random. Every byte of memory, colour RAM, the video chip and the sound chip was the same at the start of every pass.
The title and its menusFrom the loader's jump, through the title, the language and the character to the first view, beside the game in each of the six choices, with every byte the same at each stop.
Saving and loadingThe information screen's save, to tape and to disk, writes the same file as the game's, and a load puts back the same bytes; a file that is not a saved game prints INVALID FILE, as the game's does.
The page's memoryThe page carries the game's memory as the loader leaves it, with every instruction set to zero but 192 bytes of instructions the game rewrites and reads as variables, and the music driver, which the port runs on the site's 6502, the kit's simulator. The page's machine on that memory and on the whole memory runs the same, frame for frame, from the loader's jump in each language and from every one of the 199 moments.
The paceThe port executes no instructions, so the page charges each routine, and each row, byte and edge step it draws, the cycles they cost the game, fitted on some 9,700 passes timed on the simulator: play from the moments, the title's menus in each of the six choices, and the information screen opened again and again with keys shown, saves and loads. The viewport's opening steps and the keyboard's scan, which run only while the game waits for the clock, were timed alone, 2,000 calls each. From 25 moments, with the same turns, walks and looks on both, the page takes within 5 % of the game's time for the same passes, and on average 0.3 % more. From the loader's jump each of the title's keys is taken within 2 % of the game's time, each of the information screen's within 1 %, and a letter held for ten frames types twice on both, as it does on the C64.
The listingPorting a routine means reading every instruction of it. A checker that had written none of the port then compared the comments of the 114 routines it covers with the port and the instructions, and found six wrong; each has been corrected in the Source code tab.

02 · Differences

What differs from a C64

The game plays as it does on a C64, at the C64's pace. These are the places where the page cannot be the machine, and what it does instead.

On a C64On this page
A save goes to tape or disk through the KERNAL, and takes from seconds on disk to minutes on tape. The KERNAL's own messages, SAVING and LOADING among them, go to the game's own printing routine at $86CF, which the game puts in the KERNAL's output vector.The port has no KERNAL. Its own versions of SETNAM, SETLFS, SAVE and LOAD write and read the same file, the state's 106 bytes and a flag byte for every object, and keep it in this browser under the name typed, for tape and disk alike. A save or a load is instant, and none of the KERNAL's messages appear. A name the browser has no file for fails as the KERNAL's load does, and the game goes on.
The interrupt can fall between any two instructions of the main program.The interrupt runs between two of the port's routines, at the clock's time for it. A byte the interrupt changes and the main program reads in the middle of a routine (the clock, the lightning's countdown, strength) is read after the interrupts due by then have run, so the game's races come out the way the clock says rather than the way the beam would.
Each instruction takes its cycles, and a view takes as long as its polygons do.The port executes no instructions. Each routine and each row, byte and edge step it draws costs what it cost the game, fitted on the game's own timings, so a view takes about as long as on the C64 (01, The pace) and appears when its drawing is done.
The SID plays the music and the effects.The game's own music driver runs on the site's 6502 in the port, as the How it works page's tune player runs it, and the site's model of the SID plays what it writes, each frame of it as the frame is shown.
The video chip draws the screen.The site's model of the video chip draws each frame from the port's memory, with each change the port makes during the frame applied where the beam meets it.
