# Airshaft facts

The listing uses the clean-boot play snapshot `work/play-clean.vsf`, with `work/entry.vsf` for the loaded-data audit. Its disk and boot route are in the game's `orientation.md`.

- The hardware IRQ vector points to `$8D53`, which saves A, X and Y and dispatches through `$0314` or `$0316` according to the stacked status. In this snapshot `$0314` points to `$8D6F`, which sets display and sprite registers and schedules `$8E4A` at raster line `$2B`.
- A clean-boot PAL frame writes `$0314/$0315` to select `$8E4A`, `$8EB1`, `$8F1F`, `$8F5E`, `$8FE4`, `$9087`, `$90CD`, `$90E7` and `$8D6F` in that order. These are the next handler addresses written by the preceding handler, not the raster lines at which those next handlers run. The capture is `work/frame-clean.json`.
- `frame.py compare` reproduced all 104,448 pixels of that capture, both from the full frame and from the 2,547 RAM bytes retained by `frame.py trim`. The page embeds that trimmed visual data and the captured register writes.
- In that frame, the VIC reads sprite pointer `$A2` from bank 1 at `$6880`. Its 63 bytes contain a single set pixel in each of the first 20 rows and a blank final row. The interrupt handlers reuse this narrow vertical shape at several positions along the rope.
- The same frame reads sprite slots `$3A–$3E` at `$4E80–$4FBF` and character bitmap rows at `$7000–$7117`. These regions have been typed as data; the individual sprite pictures still need to be identified.
- The routine at `$AA6E` scans the keyboard and joystick. It increments the selection byte at `$A775` on a new Space press, wraps it after three positions, and uses `$A776` as the held-key latch. In VICE, three separate Space presses from the clean-boot play snapshot changed `$A775/$A776` from `01 00` through `02 01`, `00 01` and `01 01`; each release cleared the latch. The derived mode at `$9166` followed 1, 2, 3 and 1. The meaning of each mode remains open.
- The code at `$8054` clears and initializes state, copies display resources and configures the video chip before entering the loop at `$83E5`. That loop waits for `$8026` to change and alternates update paths using `$803C`.

The clean-boot executed-address capture found 1,051 instruction starts. It covers only the captured play interval; unobserved code and data remain open. The disassembler's control-flow walk requires checking against data and the capture before its blocks can be treated as authoritative.

Comparing the clean airshaft entry with `work/story-before-airshaft.vsf` in the game folder, every byte of RAM under `$D000–$DFFF` is unchanged from the preceding story state. The airshaft can still use that RAM, so its ownership remains open. In `$4C68–$7A5F`, 2,334 of 11,768 bytes agree; the load changed most of that range. The comparison does not by itself establish what the changed bytes are.

The transition at `$02A7` banks out I/O and restores `$D000–$DBFF` to `$1000–$1BFF` and `$DC00–$DFFF` to `$0400–$07FF`, then jumps to `$1000` with X and Y restored. Of the first copied range, 2,983 of 3,072 bytes match `$1000–$1BFF` in the captured preceding story. Of the second, 112 of 1,024 match the story snapshot's `$0400–$07FF`. The comparison does not account for the differences or establish every byte's ownership.

In the captured airshaft frame, the VIC uses bank 1 and selects the character set at `$7000`. All 2,048 bytes of that set are identical in the airshaft entry and play snapshots. The frame reconstruction used its visible glyphs and matched the VICE capture pixel for pixel.

The sound-stream command at `$E3EF` reads paired low and high bytes from `$E668–$E675` and `$E676–$E683` into indexed voice state. The fourteen pairs point into `$E684–$E6AB`; the structure and full extent of the pointed-to data remain open. The two tables match in the captured story, Broadway, museum and ending snapshots.

The routine at `$94C1` chooses among three mode-dependent paths that copy two eight-byte columns into `$41A8–$41BF` at a stride of three bytes. In VICE, after switching each mode and allowing 32 frames, both destination columns matched the addresses in that path’s current load operands: `$92D7/$92D7` for mode 1, `$928F/$92B7` for mode 2, and `$928F/$929F` for mode 3. The status-area image visibly changes in the three captures, showing 99, 05 and 02 respectively in that captured state. The role of those numbers remains open. In the saved frame, the VIC uses bank 1 and screen `$4400`; at raster line 251, cycle 8, the game writes sprite pointer `$06` at `$47FB`, selecting the `$4180–$41BF` slot for sprite 3. The source operands can be changed during play.

With mode 2 selected in VICE, holding fire and up for 30 frames changed the right-hand pattern pointer at `$9571–$9572` from `$92B7` to `$92AF`; the display changed from 05 to 04. Releasing fire for 60 frames left the pointer at `$92AF`. The path at `$959E` subtracts eight from that operand and clears `$94BE`; `$958A` stops the subtraction when the pointer is `$928F`.

The same VICE trial in mode 3 changed the right-hand pattern pointer at `$95BF–$95C0` from `$929F` to `$9297` while fire and up were held, with the displayed value changing from 02 to 01. Releasing fire left the pointer at `$9297`. The code at `$95EC` subtracts eight and clears `$94BF`; `$95D8` avoids subtracting when the pointer is `$928F`.

The 80 bytes at `$928F–$92DE` form ten eight-byte bitmap patterns for digits 0 through 9. A digit’s pattern begins at `$928F + 8 × digit`, which explains the eight-byte pointer step in the mode 2 and 3 decrement routines. The following eight bytes at `$92DF–$92E6` draw a percent sign. The upper status routine at `$8BDE` copies three patterns to the sprite and then changes its load operands according to `$8031`: 1 increments, while another nonzero value decrements. A processor test verifies the transitions 99 to 100 and back; what the counter measures remains open.

In a VICE trial from the clean airshaft snapshot, 240 frames holding down changed the upper counter from 00 to 11; the 16-bit values at `$A0CC` and `$A0CE` fell from `$1BE0/$1AF0` to `$1A28/$1938`. A subsequent 240 frames holding up changed the counter to 01 and those values to `$1BA4/$1AB4`. The routines at `$A28C` and `$A259` change both values by 20 and request a counter change after every two calls. This establishes the observed relationship, but what the counter measures remains open.

Three paths at `$9914`, `$999E` and `$9A1F` each copy a different 21-byte shape, increment `$8018` and add eight to the upper counter’s tens-pattern pointer. A processor test starts each path and verifies the copy, counter increment and pointer change. The destinations are successive seven-row slices of sprite slot $09 at `$4240–$427E`. In the saved frame, the game writes pointer $09 at `$47FA` on raster line 251, cycle 2, selecting that slot for sprite 2. The conditions that reach all three paths and the identity of the image remain open.

The airshaft snapshot holds 153 records of 20 bytes at `$1000–$1BF3`. At `$A2C0`, the game reads 14 indices from a row pointer, chooses the four-byte blocks at `$A35A` when `$801C` is `$1E` and those at `$A47A` otherwise, then writes the expanded bytes to `$CF00`, swapping the middle two bytes in each block. The two tables have 72 and 88 entries respectively. The remaining six bytes per record are not explained. Entry and play snapshots agree throughout the records and both tables.

Seven direct VICE calls at rows `$1BE0`, `$1AA0`, `$1500`, `$1104` and `$1000` matched the page decoder, including both table choices at each switch row. A 293-case processor comparison checks every row against the code for each table that contains its indices. The screen insertion routine at `$A5DA` selects alternating bytes from the expanded row, clears the outer cells and moves the 26-column window upward; a processor test checks both half-rows for representative records.

During a downward VICE trace, row `$1AA0` used the outer table for half 0 and the inner table for half 1. A second trace set the row pointers near the bottom before running: row `$1104` used the inner table for half 0 and the outer table for half 1. The Levels reconstruction follows those downward switches. The full path from the opening to the bottom has not been recorded, and the reverse scroll can switch tables at different points.

The airshaft snapshot’s `$1000–$1BF3` is listed as row data. The transition at `$02A7` overwrites part of it with the saved story engine before jumping to `$1000`; a static jump target alone therefore does not show that the airshaft’s row bytes execute as code. The recorded play map contains no execution starts in this range.

Seven 208-byte blocks start at `$2000` and are spaced `$D0` bytes apart. `$87D5` copies bytes 1 through 207 of the block selected by its load operand into `$7B91–$7C5F`, in the video bank; this loop leaves the byte at `$7B90` alone. The pointer list at `$88E3` names the seven blocks, with repetitions. The blocks match in the entry and play snapshots. Direct VICE calls for the first and last blocks are recorded in `airshaft-charset-animation-vice.json`; `test_airshaft_charset_animation.js` checks those and all seven copies against the processor model. The content's role on screen and the use, if any, of each block's first byte remain open.

Another seven blocks of the same size start at `$25B0`. `$88B8` copies bytes 1 through 207 of its selected block into `$7C61–$7D2F`, leaving `$7C60` untouched. The pointer list at `$890D` names all seven blocks, with repetitions, and both snapshots agree on the data. The same VICE fixture and processor test check the first and last blocks directly and all seven copies in the model. The role of these bytes and the first byte of each block remain open.

Four groups of shorter 96-byte blocks occupy `$2B60–$339F`. Their pointer lists start at `$8A71`, `$8A7F`, `$8B9E` and `$8BBE`. The copy loops write the blocks to `$7D30`, `$7DF0`, `$7D90` and `$7E50` respectively. The loops at `$89B2` and `$8A46` copy offsets 1–95, while `$8AE7` and `$8B73` copy offsets 0–95. Alternate loops at `$8995` and `$8A29` copy all 96 bytes for the first two groups. Entry and play snapshots agree on the block data. `airshaft-short-animation-vice.json` records ten forced direct calls; `test_airshaft_short_animation.js` checks them and the other block copies against the processor model. How the copied bytes are used and when the game uses each path remain open.

At `$8330`, initialization copies 1,000 screen codes from `$3400–$37E7` to `$4400–$47E7`, and five 64-byte blocks from `$3800–$393F` into sprite slots at `$4800–$493F`. The source bytes match the entry and play snapshots. `airshaft-screen-copy-vice.json` records a forced direct call, and `test_airshaft_initial_graphics.js` checks the destination against VICE and against the source bytes. The role of each sprite's final byte remains open.
