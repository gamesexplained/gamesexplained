What the program does that the manual never mentions: a pause that takes longer than it says, music that keeps the picture on, and three of its instructions that answer from the wrong place.

01 · The pause

The five-minute pause takes six minutes, and typing does not put it off

The manual says the game pauses itself after five minutes with nothing pressed. On a European machine it takes six, and only the joystick counts as something pressed.

Walk to

The count and what resets it, as the game does them: the frame interrupt counts $FC20/$FC21 down by one a frame, and the input routine ($1BAF) sets it back to 18,000 on any move or press of the joystick, and files a space when it reaches 0. Checked in VICE: the count fell by 300 in 300 frames while keys were typed, and at 0 the game paused with this line.

The game keeps a count of frames with nothing done ($FC20, $FC21). At the end of every frame the screen draws, fifty or sixty times a second, the game's frame interrupt takes one off. The input routine sets it back to 18,000 whenever the joystick moves or its button is pressed, and while a cut-scene runs, but not when a key is typed ($1BAF). When the count runs out, the routine acts as if the space bar had been pressed, and the space bar pauses the game ($234D).

18,000 frames is five minutes on an American machine, which draws 60 frames a second, and six on a European one, which draws 50. So a player in Europe gets a minute more than the manual says, and a player who only types, changing the message speed with + and - or pressing a key a script listens for, is paused all the same. The count stops while the disk is read ($13DA).

02 · The music and the disk

While music plays, the picture stays on as the next room loads

Between rooms the game turns the picture and its interrupts off while it reads the disk. Once a tune has started it leaves them on, and the music plays through the load.

From the side 1 prompt to the tune: frame interrupts in 7,780 frames
The 3,000 frames after the tune starts, with three changes of room

Measured in VICE through the opening. Before tune 95 starts, the frame interrupt ($117C) ran 6,354 times in 7,780 frames: the red is the time the picture and the interrupts were off while rooms loaded. In the 3,000 frames after it, the room changed three times (58 to 51, 55, and 49), video_off ($13F3) was called three times, and the interrupt ran in all 3,000 frames, with the picture on at every check.

When the game changes room, video_off ($13F3) blanks the screen and stops the raster interrupts, the routines the video chip calls at set lines of every frame, and video_on ($142F) brings them back. But the frame interrupt is what plays the sound (How it works). Stopping it would stop the music, so video_off checks the music's flag ($43E8) first and does nothing while a tune plays.

In the first minute of tune 95, the opening changes room three times, and each new room comes up with the picture on and the music running through the load.

03 · A wrong register

Bug: told to walk to an object it carries, an actor walks to an object in the room instead

Three instructions of the script language ask where an object is and then send an actor to it. They read the answer from the wrong place, so an object in someone's pocket sends the actor to whatever object in the room happens to share its number.

; walkActorToObject
57FF  jsr find_object     ; A: 0 carried, 1 in the room, $FF not found; Y: the slot
5802  cpy #$FF            ; only Y is looked at
5804  beq 580C
5806  jsr 08D8            ; the walk-to point of room object Y
5809  jsr start_walk
Where the object isfind_object givesWhat the instruction does
In the room, the room's object number NA 1, Y NWalks to object N's walk-to point, as it should
Not in the room, nor carriedY $FFNothing, as it should
Carried, in slot S of the inventoryA 0, Y SWalks to the walk-to point of room object S
Left in a room, while the room shown has no objectsA $FF, Y 0Walks to the walk-to point of room object 0

Traced in the code: find_object ($0767) and the three instructions, walkActorToObject ($57F1), putActorAtObject ($580D), and loadRoomWithEgo ($548D). Whether any of the game's scripts asks for a carried object is not known.

find_object ($0767) answers in two of the processor's registers, A and Y. A says where the object is: 0 for an object someone carries and 1 for one in the room. Y says which slot: the inventory slot for a carried object, the index among the room's objects for one in the room, and $FF when the object is not found. The three instructions look only at Y, and take anything but $FF to mean an object in the room. They then read the walk-to point from the room's object tables at index Y ($08D8).

For a carried object, Y is its slot in the inventory, so the actor walks to, or is put at, the room object that sits at that index. And in a room with no objects, find_object gives up before its search with Y still 0, so the walk goes to whatever the tables hold for object 0. loadRoomWithEgo, which takes the actor into a new room and puts it at an object there, makes the same test after it has loaded the room ($54DE), so a carried object puts the actor at the point of the room object with its slot number.

04 · A wrong index

Bug: the position of an actor in another room is read from the wrong memory

getActorX and getActorY give an actor's position. For an actor in another room they read the wrong memory, so a script gets a number that has nothing to do with the actor.

; getActorX
5C9F  tax                 ; X: the actor
5CA0  ldy FD56,x          ; Y: its walk slot, $FF when it is not in the room
5CA3  bmi 5CAB
5CA5  lda FCE6,y          ; in the room: X from its walk slot
5CA8  jmp 5CAE
5CAB  lda FFB7,y          ; not: meant to be FFB7,x

Traced in the code: getActorX ($5C99) and getActorY ($5CB2).

An actor in the room has a walk slot, and its position is read from there ($FCE6). An actor elsewhere keeps its position in its own table, one byte for each of the 13 actors ($FFB7 for X, $FFAA for Y). The instructions index that table with Y, which holds the walk slot, $FF, instead of with X, which holds the actor. The address runs past the top of memory and wraps round: getActorX reads $00B6, a flag for the message line, and getActorY reads $00A9, the same for every actor.

05 · A message nobody sees

Bug: a save that the disk will not take is never noticed

Saving has a "Disk Error, push button to continue." and a retry for a sector the drive will not write. Neither can happen.

; disk_write, for each sector
3AF5  jsr bus_write_sector
3AF8  bcc 3B08            ; carry clear: written
...                       ; "Disk Error", wait for the button, try again

; bus_write_sector, at its end
3BF0  clc                 ; always clear
3BF1  rts

Traced in the code: disk_write ($3AD1) and bus_write_sector ($3BCB).

The game saves by sending each sector to its own program in the disk drive ($3BCB). A read waits for the drive's program to answer, and an error code from the drive sets the carry ($3BF8). A write sends the command and the 256 bytes and returns with the carry clear, which disk_write ($3AD1) takes to mean the sector went on to the disk. So whatever happens at the drive, the game takes every sector as written and says nothing.

06 · The music's room

Secret: the music is stored with a room that has no picture

Every resource on the disks belongs to a room. The music's program and all four tunes belong to room 47, which has nothing to show.

From the resource index the game reads at start-up ($6E4E for the rooms, $7142 for the sounds' rooms) and the files on side 1.

The game finds a resource by the room it lives with and an offset in that room's file. The rooms are places in the game, except this one: room 47 is the smallest room in the game, with a picture of one character repeated, and its file holds nothing but the music. No costume or script lives there. It is drawn on the Maps tab with the rest.

07 · A sound that ends twice

Sound 36 is over before its filter part has finished

The engine counts how many of a sound's voices are playing. Sound 36 has a part for the filter as well, and it is still running when the count says the sound is over.

After 162 frames of sound 36, its two voices end and its count, which a script reads to ask whether the sound is still playing, drops to 0. Its third part, which works the chip's filter, is still on its channel, and the engine goes on stepping it every frame. No voice is left to be heard through the filter.

Seen on the game's own sound engine, run on the site's model of the processor for every effect on the disks (the test beside the Sound player). Sound 36 is the only one.

Each voice a sound starts adds one to the sound's count ($3F3A), and each voice that ends takes one off ($3EB6). A filter part is started by another routine, which leaves the count alone ($3E4C), and its end takes nothing off. isSoundRunning, which scripts use to wait for a sound, reads that count ($571C). So the count follows a sound's voices only, and a filter part that outlasts them runs on uncounted.
