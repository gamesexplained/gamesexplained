# Jumpman: verified facts

## Evidence and image

Address-based statements below are traced from this disk's instructions and data. **Live input** means ordinary controls applied to a running saved game. **Controlled live** means the original code ran in VICE with specified memory or entry conditions. **CPU checked** means unchanged instructions ran in the kit's 6502 simulator with declared inputs; it does not establish a naturally reachable game state.

The supplied disk identifies itself as `JUMPMAN REV 1.0`. Its loader at `$0800` enters `$0811`, loads the 32,768-byte `INTRO.SYS` at `$2000`, tests `$9FFF`, and hands over at `$2F03`. The canonical entry snapshot stops before that first instruction: every byte at `$2000-$9FFF` matches the file. This preserves authored sprites at `$8E40` that ordinary play overwrites.

There are 32 native 2,048-byte level files: `PLF01`–`PLF24`, `PLF2A`–`PLF2C`, and `PLF26`–`PLF30`. Each loads at `$3800`; `$74F3` copies `$3800-$3FFF` to active [$3000-$37FF](source-plf01.html#3000). **Live loader captures** stopped at `$7514`, before drawing or initialization, and matched all 2,048 disk bytes for every file. Each overlay has its own part and Source page, displayed over the original resident/startup listing. This is a source composition, not a single frozen machine state: all 32 native level entries have the same 224 cleared boot-code bytes and 20 self-modified operand bytes in the resident code. The capture route and these expected listing warnings are explained in the orientation. Shared level-header links use PLF01 as an example; private addresses in each level’s facts link to its own file. `SCORES` is a separate 1,024-byte file loaded at `$2000`.

Evidence: `orientation.md`, `work/level-captures.json`, the entry and level snapshots, and their corresponding extracted files. The machine is PAL C64SC; host elapsed time is not used for game timing. The coverage ledger explains all 90,263 included bytes across 33 parts: 24,727 resident bytes and all 65,536 overlay bytes. This measures annotation coverage, not the correctness of every interpretation. Byte and execution checks establish the results described here; independent maintainer verification is separate. The resident part excludes the 320 bytes in the original startup sprite slots in the level-owned workspace, documented in its own facts. Machine memory, generated output and specifically justified padding are outside that denominator; retained overlay tails remain included.

## Mystery Maze selection and reveal boundaries

**CPU checked:** Jungle cleanup at [$3214](source-plf24.html#3214) was executed for all 256 reserve bytes: 0–2 selects A, 3–4 selects B, and 5–255 selects C. Value 255 is the eliminated-player sentinel, so that cleanup result does not establish a playable 256-life transition. **Controlled live:** at initialized Jungle, setting bombs to zero and reserves to2/4/5 followed the ordinary completion path and loaded PLF2A/2B/2C respectively. All2,048 bytes of each native loaded overlay matched its disk file. These tests bypass collecting Jungle's bombs, so a full legal Jungle-to-maze route remains unverified.

Each of the three original reveal routines was executed for all 131,072 combinations of X=0…511 and Y=0…255: **393,216 cases total**. It accepts hardware X=32…321 and Y=50…216. Y=50…57 reveals eight cells; Y=58…216 reveals twelve. The column is `floor((X-32)/8)`. Let `C=(X>>2)&1` and let origin be 48 in the eight-cell case or 56 otherwise; the first row is `floor((Y-origin-1+C)/8)`. Thus the right half of each eight-pixel column crosses a row boundary one scanline earlier because the Y subtraction inherits carry from the X shift.

No accepted case wraps a row or writes outside the display. The union of reachable reveal offsets is 0…918, ending at matrix `$8396` and colour `$DB96`; cell 919 and display rows 23–24 are never painted by this routine alone. Initialization clears exactly 1,000 colour/matrix cells while preserving bitmap and sprite pointers, and later reveals persist. This verifies original code for controlled coordinates; it does not establish legal joystick routes to every coordinate (`work/followup-progression/proof.json`). **Controlled live:** six boundary coordinates per variant, eighteen calls total, matched the exact matrix destinations, including the X32/X36 carry shift and rejected X322.

## Interactive bomb scenery comparisons

The map viewer starts with each file's stored initial stream, erases one selected bomb with `$56BC`/shape`$7F27`, then executes the drawing pointer from its seven-byte record. **CPU checked:** all397 records in the32 initial bomb tables match the original collector tail `$567A-$569C` across every8,192-byte bitmap. Forward and reverse drawing sequences for each table also match, giving1,191 comparisons. Each starting layout was independently drawn by original `$4D0F`. The page uses only referenced drawing/shape excerpts. Per-bomb material changes and snapshot hashes are retained in the private comparison records.

These comparisons deliberately omit the preceding private callbacks, score handling and player movement. They establish the drawing operations, not legal pickup orders or all consequences of collection. The viewer resets to the opening layout for each choice. It does not show Runaway's randomized initial placement, Grand Puzzle III's second stage, hidden-platform colour changes or drawings scheduled later by a moving actor. Such rules remain in the level notes. Added/removed highlights compare the two-bit bitmap materials; changing one material into another is marked separately. Bomb numbers select records, including special records that need not be visible in the opening layout.
