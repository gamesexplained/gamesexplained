## 0.0.156 · 2026-10-12 · Clowns (C64) · Vai

- **A cartridge that holds GAME low is analysed from its `.crt`, and the
  video chip reads its ROM.** Clowns is an Ultimax cartridge: its 8 KB sit
  where the KERNAL was, the snapshot's RAM image holds only the power-on
  pattern there, and the font and two sprites the screen shows are read by
  the video chip straight from the ROM's top 4 KB. The listing was built
  from the `.crt`, and a frame drawn with those 4 KB in the video chip's
  view matched the emulator to the pixel; without them it drew blank. The
  emulator's own call for the video chip's state answered with RAM while
  the cartridge was in, which stopped the frame recorder until it read the
  chip through the I/O bank. The six entries below hold the measurements.
  On 12 October 2026 no other game folder held an Ultimax cartridge, so
  they are here and not in `c64-reference`.
- **An Ultimax cartridge is a `.crt` whose header holds GAME low and EXROM
  high** (byte `$19` = 0, byte `$18` = 1), the configuration of Commodore's
  MAX Machine games. `kit/c64/crt.py <file.crt>` prints the lines. What
  follows was measured in VICE x64sc 3.13.2 with an 8 KB one at
  `$E000`-`$FFFF` (11 October 2026).
- **The processor sees the cartridge in place of the KERNAL** (with `$01`
  at `$17` after the reset and `$E5` as the game set it): the reset, IRQ
  and NMI vectors at `$FFFA` are the cartridge's, and the KERNAL never
  runs, so the game sets up the chips itself. VICE's `cpu` and `cart` banks
  read the ROM at `$E000`; its `ram` bank reads the RAM beneath, which
  holds the power-on pattern.
- **The program is in the `.crt`, not the snapshot.** A snapshot's RAM
  image holds the RAM beneath the cartridge. A cartridge of one bank in a
  game folder with no parts is its own image:
  `tools.py r2000 <game>/work/<file>.crt` starts the disassembler on it,
  and `listing.py <game> <game>/work/<file>.crt` builds the listing from
  it. The RAM the game uses is runtime state, for `coverage.exclude`.
- **The video chip sees the top 4 KB of the cartridge at `$3000`-`$3FFF`**
  of its bank, so a character set or sprite pointed there is read from the
  ROM at `$F000`-`$FFFF` (a frame drawn that way matched the emulator's
  picture to the pixel). `kit/c64/frame.py capture` records those 4 KB as
  the frame's `ultimax` and `C64.renderFrame` draws from them; a page may
  embed them, as the game's own bytes. Where the character ROM shows the
  chip in this configuration was not measured.
- **`vice_vicii_get_state` answers with RAM** while such a cartridge is
  attached: the power-on pattern for every register and line 256
  throughout. Read the video chip through the `io` bank instead
  (`frame.py`'s `vic()` does).
- **The executed-address record marks the cartridge's instructions as RAM
  execute**, so `kit/c64/codemap.py dump` keeps them without `--under-rom`.
- **Code compiled from a high-level language has a calling convention to
  find first.** Half of Clowns opens every procedure with one call that
  builds a frame on a stack of its own and passes its arguments past the
  caller's frame, keeps its globals in the main program's frame, prints
  text from the bytes after a call, and reaches the machine code only by
  number through one table. Reading those few routines first turned the
  rest into a list of procedures with named arguments, and the table gave
  the trace 1.4 KB of code no instruction referred to.
- **The comments that were wrong were about registers and modes, not
  purpose.** A sample of 60 found 9 wrong: which register a routine
  returns its result in, a constant table read off by one entry, and text
  said to appear that the attract mode never shows. Each was a detail
  written from the call site in front of the annotator rather than from
  the routine's end, and from the game rather than from the attract mode
  that runs the same code with its flags cleared.
